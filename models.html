เรื่องที่เกิดจริงบนเครื่องนี้

หมวดนี้ยาวเพราะเรื่องนี้มี สามเรื่องซ้อนกัน ถ้าอ่านแค่บรรทัดเดียวจะเข้าใจผิด ต้องไล่ทีละชั้น

  1. บนเครื่องมี สองคำสั่งคนละไฟล์ ที่ชื่อคล้ายกัน
  2. โปรแกรมที่คุยกับโมเดลไม่ได้ดูไฟล์บนดิสก์ แต่ดู ชื่อที่ vLLM ประกาศ
  3. ตัวเลข RAM ที่สูงส่วนใหญ่คือ ที่จองล่วงหน้า ไม่ใช่ไฟล์โมเดลโตขึ้น

อาการที่เจอจริงมีสองอย่างพร้อมกัน

  • รัน start-qwen35 แล้ว Hermes ส่งข้อความไม่ได้ / ขึ้นว่าโมเดลไม่มี (HTTP 404)
  • รัน start-qwen35 แล้ว RAM ดูสูงผิดปกติ เมื่อเทียบกับตอนรัน qwen35-start

จอง RAM

สูตรเก่ากัน 82% สูตรใหม่กัน 40% ไฟล์โมเดลไม่ได้โต

สิ่งที่ ไม่ได้ พัง: ไฟล์โมเดลบนดิสก์ไม่หาย Hermes แดชบอร์ดไม่พัง Open WebUI ยังคุยได้ด้วยชื่อสั้น ปัญหาอยู่ที่ ชื่อที่เรียก กับ สูตรจอง RAM

อ่านต่อตามหัวข้อซ้ายมือ ห้ามข้าม สองคำสั่ง → Linux หาคำสั่งยังไง → ข้างในคำสั่ง → ชื่อสามชั้น → RAM → สิ่งที่แก้แล้ว แล้วค่อยไป เปิดโมเดล

สองคำสั่งนี้ไม่ใช่คำสั่งเดียวกัน

บนเครื่องนี้มีคำสั่งสองตัวที่คนพิมพ์สลับกันบ่อย เพราะมีคำว่า qwen35 เหมือนกัน แต่ขึ้นต้นคนละแบบ และไปเปิดคนละคอนเทนเนอร์

Linux หาคำสั่งยังไง และทำไมกด Tab แล้วได้คนละตัว

เมื่อพิมพ์ชื่อคำสั่งแล้วกด Enter เชลล์ไม่ได้เดา มันเดินหาไฟล์ตามตัวแปร PATH จากซ้ายไปขวา เจอชื่อตรงกันตัวแรกแล้วหยุด

บนเครื่องนี้ PATH ขึ้นต้นด้วย /home/dgxspark/.local/bin แล้วค่อยถึง /usr/local/bin

พิมพ์ start-qwen35 เชลล์เดิน PATH จากซ้าย → เจอที่ ~/.local/bin ก่อน → สูตรสตูดิโอ
↓ คนละชื่อ ไม่ทับกัน
พิมพ์ qwen35-start ไม่มีใน ~/.local/bin → ไปเจอที่ /usr/local/bin → สูตรเก่า
↓ กับดัก Tab
พิมพ์แค่ qwen35 แล้วกด Tab เชลล์เติมเป็น qwen35-start เพราะไฟล์นั้นขึ้นต้นด้วย qwen35
echo $PATH

ดังนั้น

  • พิมพ์ start-qwen35 → เจอที่ ~/.local/bin ก่อน → เปิดสูตรสตูดิโอ
  • พิมพ์ qwen35-start → ไม่มีไฟล์ชื่อนี้ใน ~/.local/bin → ไปเจอที่ /usr/local/bin → เปิดสูตรเก่า

สองชื่อนี้ไม่ทับกันใน PATH เพราะสะกดไม่เหมือนกัน ทั้งคู่จึงเรียกได้ตลอด ใครพิมพ์ชื่อไหนก็ได้ตัวนั้นจริง ๆ

กับดักที่พบบ่อย: กด Tab เติมคำ

  1. เปิดเทอร์มินัล

    กด Ctrl + Alt + T

  2. พิมพ์แค่ qwen35 แล้วกด Tab

    เชลล์จะเติมเป็น qwen35-start เพราะไฟล์นั้นขึ้นต้นด้วย qwen35

  3. ถ้าต้องการสูตรสตูดิโอ ต้องพิมพ์ start- ก่อน

    พิมพ์ start-q แล้วค่อยกด Tab จะได้ start-qwen27 หรือ start-qwen35

  4. ก่อนกด Enter ดูชื่อเต็มบนบรรทัด

    ต้องเป็น start-qwen35 ทั้งคำ ห้ามเหลือแค่ qwen35-start

อย่าพิมพ์ start-qwen35 แล้วตามด้วย qwen35-start ในอีกแท็บ คำสั่งหลังจะพยายามเปิด nemoclaw-vllm ทับพอร์ต 8000 ของตัวที่เพิ่งเปิด

แต่ละคำสั่งทำอะไรข้างใน ทีละขั้น

อย่าคิดว่าสองคำสั่ง “เปิดโมเดลเดียวกันคนละทาง” มันเปิดคนละคอนเทนเนอร์ และปิดตัวอื่นไม่เหมือนกัน

เมื่อรัน start-qwen35

ไฟล์ ~/.local/bin/start-qwen35 มีแค่บรรทัดเดียว คือไปเรียกสคริปต์กลาง

cat ~/.local/bin/start-qwen35

ผลที่ต้องเห็น

#!/usr/bin/env bash exec /home/dgxspark/ai/open-webui/llm start qwen35

จากนั้นสคริปต์ ~/ai/open-webui/llm ทำตามนี้เป๊ะ

  1. พิมพ์ Stopping any running model...

    แล้วปิดทุกตัวในรายการ vllm-nemotron vllm-qwen27 vllm-qwen35 nemotron-vllm nemoclaw-vllm qwen36-27b

  2. เปิด Open WebUI ถ้ายังไม่เปิด

    หน้าเว็บอยู่ที่พอร์ต 18473 ไม่กินพอร์ต 8000

  3. สร้างแล้วเปิดคอนเทนเนอร์ vllm-qwen35 จาก docker-compose

    ใช้โปรไฟล์ qwen35 ในไฟล์ ~/ai/open-webui/docker-compose.yml

  4. รอ API ที่พอร์ต 8000 สูงสุด 720 วินาที

    ทุก 15 วินาทีจะพิมพ์ still loading... รอบแรกหลังคอมไพล์เคอร์เนลอาจนาน 5–6 นาที อย่ากด Ctrl+C

  5. เมื่อ Ready จะพิมพ์ชื่อโมเดลที่ API ประกาศ

    สูตรปัจจุบันต้องขึ้นทั้ง nvidia/Qwen3.6-35B-A3B-NVFP4 และ Qwen3.6-35B

เมื่อรัน qwen35-start

ไฟล์นี้เป็นลิงก์ไป /usr/local/bin/qwen-switch สคริปต์นั้นดูชื่อที่ถูกเรียก ถ้าชื่อเป็น qwen35-start จะทำแบบนี้

  1. ตรวจว่ามีคอนเทนเนอร์ชื่อ nemoclaw-vllm

    ถ้าไม่มี จะพิมพ์ ไม่พบ container แล้วจบ ไม่ได้ไปสร้างจาก compose ของสตูดิโอ

  2. ถ้า qwen36-27b เปิดอยู่ จะปิดแค่นั้น

    มัน ไม่ปิด vllm-qwen35 หรือ vllm-nemotron นี่คือเหตุที่เคยชนพอร์ต 8000

  3. docker start nemoclaw-vllm

    แค่ปลุกคอนเทนเนอร์เก่าที่เคยสร้างไว้ตอนลง NemoClaw ไม่ได้อ่านสูตรใหม่ใน docker-compose.yml

  4. รอ API ที่พอร์ต 8000 สูงสุด 600 วินาที
ถ้ารัน start-qwen35 จน Ready แล้วไปรัน qwen35-start ทับ สูตรเก่าจะพยายามปลุก nemoclaw-vllm ทั้งที่พอร์ต 8000 ถูกจองแล้ว อย่าทำ

ชื่อโมเดลมีสามชั้น คนละอย่างกัน

จุดนี้คือเหตุที่ Hermes พังทั้งที่โมเดลโหลดอยู่แล้ว ต้องแยกสามชั้นให้ขาด

ชั้น 1 · ไฟล์บนดิสก์ โฟลเดอร์น้ำหนักโมเดล ~/.cache/huggingface/hub/models--nvidia--Qwen3.6-35B-A3B-NVFP4 ประมาณ 22 GB คนไม่ได้อ่านโฟลเดอร์นี้ตรง ๆ
↓ vLLM โหลดไฟล์นี้ แล้วประกาศชื่อให้คนอื่นเรียก ตามค่า --served-model-name
ชั้น 2 · ชื่อที่ API ประกาศ ถามได้ที่ http://127.0.0.1:8000/v1/models ช่อง id ใน JSON คือชื่อที่เรียกได้จริง
↓ โปรแกรมแชทส่งชื่อนี้กลับไปในคำขอ /v1/chat/completions
ชั้น 3 · ชื่อที่โปรแกรมยิง Hermes ยึดชื่อเต็ม nvidia/Qwen3.6-35B-A3B-NVFP4 อย่างเดียว Open WebUI เลือกชื่อไหนในรายการก็ได้

ชั้น 1 ไฟล์บนดิสก์ไม่เปลี่ยน

ทั้ง start-qwen35 และ qwen35-start อ่านน้ำหนักก้อนเดียวกัน ไม่ได้โหลดโมเดลคนละเวอร์ชัน

ls ~/.cache/huggingface/hub | grep Qwen3.6-35B

ต้องเห็นโฟลเดอร์ models--nvidia--Qwen3.6-35B-A3B-NVFP4

ชั้น 2 ชื่อที่เสิร์ฟ ตั้งใน docker-compose

ใน ~/ai/open-webui/docker-compose.yml บริการ qwen35 ตอนนี้มีสองชื่อ

--served-model-name nvidia/Qwen3.6-35B-A3B-NVFP4 Qwen3.6-35B

บรรทัดแรกหลัง --served-model-name คือชื่อหลัก บรรทัดถัดไปที่ไม่ขึ้นต้นด้วย -- คือชื่อสำรอง ไฟล์โมเดลยังก้อนเดียว แต่ API ยอมรับทั้งสองชื่อ

ตรวจของจริงจากคอนเทนเนอร์ที่กำลังรัน

docker inspect vllm-qwen35 --format '{{range .Config.Cmd}}{{println .}}{{end}}'

ชั้น 3 Hermes ยิงชื่อเต็มเท่านั้น

ดูจากคำสั่งจริงบนเครื่องนี้

nemoclaw hermes status

บรรทัดที่ต้องอ่าน

  • Model: nvidia/Qwen3.6-35B-A3B-NVFP4 = ชื่อที่ Hermes จะใส่ในคำขอทุกครั้ง
  • Provider: vllm-local = ไม่โหลดโมเดลในกรงเอง
  • Inference (vllm backend): healthy (http://127.0.0.1:8000/v1/models) = โฮสต์พอร์ต 8000 ตอบและมีชื่อที่ตรง

Open WebUI คนละแบบ มันถาม /v1/models แล้วโชว์ทุก id ให้เลือก ดังนั้นชื่อสั้นอย่างเดียวก็คุยได้

ทำไมสูตรเก่าถึงได้ 404

สูตรเก่าของ start-qwen35 ประกาศแค่ Qwen3.6-35B

  • Open WebUI เห็นชื่อสั้น → เลือกได้ → คุยได้
  • Hermes ยิงชื่อเต็ม nvidia/Qwen3.6-35B-A3B-NVFP4 → vLLM หา id นี้ไม่เจอ → ตอบ HTTP 404 ว่าโมเดลไม่มี

ทดลองอาการนี้บนเครื่องได้โดยยิงชื่อที่ไม่มีจริง โมเดลที่โหลดอยู่จะไม่ถูกปิด

curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen3.6-35B-WRONG","messages":[{"role":"user","content":"hi"}]}'

สูตร qwen35-start ประกาศชื่อเต็มพอดี Hermes จึงใช้ได้ เลยดูเหมือน “คำสั่งนั้นถูกกว่า” ทั้งที่จริง ๆ แล้วเป็นคนละคอนเทนเนอร์ที่บังเอิญตั้งชื่อถูก

ทำไม RAM สูงผิดปกติ

DGX Spark ชิป GB10 ใช้หน่วยความจำก้อนเดียวทั้งระบบและ GPU รวมประมาณ 121 GiB ไม่มีแรมการ์ดแยก ตัวเลขใน free -h จึงรวมของโมเดลด้วย

สูตรเก่า 0.82กันไว้ ~99 / 121 GiB
available เหลือไม่กี่ GB เครื่องแน่น ทั้งที่ไฟล์โมเดลยัง 22 GB
สูตรตอนนี้ 0.40กันไว้ ~48 / 121 GiB
เหลือที่ให้เบราว์เซอร์ Open WebUI Hermes และระบบ

ไฟล์โมเดลไม่ได้โต

น้ำหนักบนดิสก์ยังประมาณ 22 GB เท่าเดิม ทั้งตอน RAM ดู 100 GB และตอนดู 60 GB ดังนั้นปัญหาไม่ได้อยู่ที่ “โหลดโมเดลคนละไฟล์”

vLLM กันพื้นที่ตอนสตาร์ท

ค่า --gpu-memory-utilization บอก vLLM ว่าให้กันสัดส่วนเท่าไรของหน่วยความจำที่มองเห็น ไว้ให้น้ำหนักโมเดลบวก KV cache

ของเครื่องนี้ประมาณ 121 GiB สูตรเก่า 0.82 × 121 ≈ 99 GiB ถูกกันไว้ตั้งแต่ยังไม่ได้คุย สูตร Hermes / สูตรใหม่ 0.40 × 121 ≈ 48 GiB

ส่วนที่กันเกิน 22 GB คือ KV cache ที่เตรียมไว้ให้บทสนทนายาว อ่านต่อที่ KV cache ไม่ได้แปลว่าโมเดลกิน 100 GB ทั้งก้อนตลอดเวลา

อ่าน free -h ยังไง ห้ามดูแค่ used

  1. รันคำสั่งนี้
    free -h
  2. ดูคอลัมน์ available ไม่ใช่ free

    free คือที่ว่างเปล่าจริง ๆ ส่วนที่ระบบเก็บแคชไฟล์จะโชว์ใน buff/cache และยังคืนให้โปรแกรมได้ คอลัมน์ที่บอกว่า “ยังเปิดอย่างอื่นได้อีกไหม” คือ available

  3. ตัวเลขปกติหลังเปิด Qwen 35B สูตร 40%

    วันที่ 17 สิงหาคม 2026 เครื่องนี้ใช้ไป 61 GiB เหลือ available 59 GiB มีแคชอีกประมาณ 30 GiB

เลข 61 GiB ไม่ได้แปลว่าโมเดลกินคนเดียว ในนั้นมี Open WebUI, ComfyUI, กรง Hermes, ระบบ และแคชด้วย ส่วนที่ vLLM กันไว้ตามสูตร 40% ประมาณ 48 GiB

อยากคืน RAM ให้รัน stop-model อย่าไปปิดแท็บเบราว์เซอร์อย่างเดียว แท็บไม่ใช่ตัวที่จอง 48–100 GB

สลับไป Qwen 35B ทีละขั้น

ทำตามลำดับนี้บนเครื่อง DGX ใช้ start-qwen35 อันเดียว อย่าพิมพ์ qwen35-start คู่กัน ถ้ายังไม่ได้อ่าน เรื่องที่เกิดจริง ให้อ่านก่อน

  1. เปิดเทอร์มินัลบนเครื่อง DGX

    กด Ctrl + Alt + T ต้องเป็นเทอร์มินัลบนตัวเครื่องหรือ SSH เข้าเครื่องนี้ ไม่ใช่เทอร์มินัลในกรง Hermes

  2. ดูว่าตอนนี้มีโมเดลอะไรเปิดอยู่
    llm-status
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

    จำไว้ว่าเห็นอะไร ถ้าเห็น nemoclaw-vllm vllm-nemotron หรือ vllm-qwen27 ไม่ต้องปิดมือเอง ข้อถัดไปปิดให้

  3. ยืนยันว่าจะพิมพ์ชื่อถูก
    which start-qwen35

    ต้องได้ /home/dgxspark/.local/bin/start-qwen35 ถ้าได้ path อื่น หยุดแล้วอ่าน Linux หาคำสั่งยังไง

  4. พิมพ์ชื่อคำสั่งให้ครบแล้วกด Enter
    start-qwen35

    ต้องขึ้นต้นด้วย start- อย่าใช้ qwen35-start อย่าเปิดแท็บที่สองไปรันคำสั่งสลับโมเดลอีกตัว

  5. อ่านบรรทัด Stopping any running model...

    ถ้ามีสูตรเก่าเปิดอยู่ จะถูกปิดในขั้นนี้ เพื่อไม่ให้แย่งพอร์ต 8000 รอจนผ่านบรรทัดนี้ก่อน

  6. อ่านบรรทัด Starting qwen35... แล้ว Waiting for model API

    ตอนนี้ vLLM กำลังโหลดน้ำหนัก คอมไพล์เคอร์เนล และกันพื้นที่ KV cache

  7. รอจนขึ้น Ready ห้ามกด Ctrl+C

    รอบแรกหลังรีบูตหรือหลังอัปเดตอิมเมจอาจนาน 5–6 นาที ทุก 15 วินาทีจะขึ้น still loading... นั่นปกติ เพดานรอคือ 720 วินาที

  8. ดูชื่อโมเดลที่พิมพ์ออกมาหลัง Ready

    ต้องมีบรรทัด model: nvidia/Qwen3.6-35B-A3B-NVFP4 ถ้ามีแค่ Qwen3.6-35B ให้หยุด แล้วยิง docker logs --tail 80 vllm-qwen35 แล้วย้อนไปดูว่าแก้สูตรใน compose หลุดหรือยัง

  9. อย่าเปิดโมเดลใหญ่อีกตัวค้างไว้

    อย่าไปรัน start-nemotron หรือ qwen35-start ทับ เปิดโมเดลใหญ่ได้ทีละตัว

ถ้าขึ้น Timed out ไม่ได้แปลว่าคำสั่งผิด ให้ดูล็อกก่อน รอบคอมไพล์แรกยาวมาก ดูด้วย docker logs --tail 80 vllm-qwen35 ถ้ายังโหลดอยู่ให้รอต่อ แล้วค่อยรัน llm-status อีกครั้ง

ตรวจว่า Qwen 35B ใช้ได้จริง

ทำครบทั้ง 8 ข้อ อย่าข้าม ถ้าข้อไหนไม่ผ่าน อย่าเพิ่งไปคุยใน Hermes แล้วสรุปว่าเอเจนต์พัง

  1. ถามสถานะรวม
    llm-status

    ต้องได้ Model container: vllm-qwen35 (running) และ API model: มีทั้งชื่อเต็มกับชื่อสั้น

  2. ถาม API ตรง ๆ
    curl -s http://127.0.0.1:8000/v1/models | python3 -m json.tool

    ใน JSON ต้องมี "id": "nvidia/Qwen3.6-35B-A3B-NVFP4" ถ้ามีแค่ชื่อสั้น Hermes จะ 404

  3. ดูคอนเทนเนอร์ที่เปิดอยู่
    docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

    ต้องเห็น vllm-qwen35 สถานะ Up ผูก 0.0.0.0:8000->8000/tcp และต้องไม่เห็น nemoclaw-vllm พร้อมกัน

  4. ยืนยันสูตรในคอนเทนเนอร์
    docker inspect vllm-qwen35 --format '{{range .Config.Cmd}}{{println .}}{{end}}'

    ต้องเห็น --gpu-memory-utilization เป็น 0.40 และ --served-model-name ตามด้วยชื่อเต็ม

  5. ดู RAM
    free -h

    สูตร 40% ทั้งระบบมักใช้ราว 60 GiB และยังเหลือ available หลายสิบ GiB ถ้า available เหลือไม่กี่ GB ทั้งที่เพิ่งเปิด Qwen 35B อย่างเดียว ให้สงสัยว่ายังใช้สูตร 0.82

  6. ถาม Hermes ว่าเห็นโมเดลหรือยัง
    nemoclaw hermes status

    บรรทัด Model: ต้องเป็นชื่อเต็ม บรรทัด Inference (vllm backend) ต้องเป็น healthy ห้ามเป็น unavailable

  7. ทดสอบ Open WebUI

    เปิด http://127.0.0.1:18473 กด F5 คลิกตัวเลือกโมเดล มุมบน เลือกชื่อเต็มหรือชื่อสั้น แล้วส่งข้อความสั้น ๆ เช่น สวัสดี ต้องได้คำตอบ

  8. ทดสอบ Hermes

    เปิด http://127.0.0.1:18789/ จากเครื่อง DGX เข้าเมนู CHAT สร้างห้องใหม่หรือส่งในห้องที่ยังไม่มี error ค้าง ข้อความสั้น ๆ ต้องไม่ขึ้นว่าโมเดลไม่มี

ถ้าข้อ 2 ผ่านแต่ข้อ 6 ไม่ผ่าน ให้รีเฟรชสถานะ Hermes อีกครั้งหลัง API Ready ประมาณ 10 วินาที บางรอบเกตเวย์ยังแคชของเก่า

เปิดปิดเฉพาะหน้าเว็บ

อันนี้คนละเรื่องกับโมเดล ปิดเว็บแล้วโมเดลยังกิน RAM อยู่

  1. ปิดหน้าเว็บแต่ไม่แตะโมเดล
    stop-webui
  2. เปิดหน้าเว็บกลับ
    start-webui
  3. เข้า http://127.0.0.1:18473 อีกครั้ง แล้วล็อกอินถ้าถาม

KV cache คืออะไร

เมื่อโมเดลตอบ มันดูข้อความทีละคำ และจำผลคำนวณของคำเก่าไว้ในหน่วยความจำ ก้อนนั้นชื่อ KV cache (Key-Value cache)

ถ้าไม่มี cache ทุกครั้งที่จะพิมพ์คำใหม่ โมเดลต้องอ่านข้อความเก่าทั้งก้อนใหม่หมด บทสนทนายาวจะช้าลงเรื่อย ๆ

vLLM จึงกันที่สำหรับ cache ไว้ตั้งแต่สตาร์ท ไม่ได้รอให้คุยยาวแล้วค่อยขอทีละนิด ดังนั้นพอเปิดโมเดล RAM จะกระโดดทันที แม้ยังไม่ได้พิมพ์อะไร
